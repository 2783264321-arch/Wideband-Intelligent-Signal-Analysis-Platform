# M8.6B Batch Analysis Package - Design Spec

Date: 2026-09-06
Status: Design approved in chat; awaiting written-spec review
Parent spec: `docs/superpowers/specs/2026-09-06-m8-6-dataset-benchmark-design.md`
Shared baseline: `feature/v1-core @ d93913c98c3cb528de4cda831bdf583f25f4ee29`

This document refines the M8.6 master design for M8.6B only. Where this document is more specific than the master spec on Batch Analysis Package transport, recording identity, batch import atomicity, idempotency, historical export, or real-import acceptance, this document is authoritative for M8.6B. It does not change the already implemented M8.6A benchmark protocol or domain model.

## 1. Purpose

M8.6B adds a reproducible transport and import path for dataset-scale external Pipeline results.

The first real use case is the frozen historical SpaceNet advanced/test result set for:

- pipeline ID: `zoomspec_yolo26n_aug_combined_frn_v3`
- pipeline version: `1.0.0`
- label space: `spacenet_14`
- dataset: `SpaceNet`
- split: `test`
- expected samples: 2,500
- historical prediction rows: 33,373

M8.6B must convert these results into ordinary platform `AnalysisRun` and `DetectionResult` rows without rerunning inference and without introducing a new runtime execution model.

## 2. Non-goals

M8.6B does not add:

- `BatchRun`;
- `BatchImportModel`;
- a `batch_id` database column;
- a generic `Dataset` domain entity;
- a generic import Job entity;
- Redis, Celery, Postgres, or another task queue;
- frontend benchmark pages;
- automatic DatasetEvaluation creation;
- automatic benchmark execution;
- live GPU inference;
- historical model reruns;
- model training;
- permanent storage of uploaded Batch ZIP archives;
- changes to Analysis Package v1 wire semantics;
- changes to the M8.6A `physical_tf_detection_ap_v1` evaluator;
- changes to M8.5 Hungarian matching semantics.

## 3. Architectural invariants

1. A Batch Analysis Package is a transport container, not a domain entity.
2. A successful batch import expands into ordinary completed `AnalysisRun` rows and ordinary `DetectionResult` rows.
3. Every imported child remains semantically one Analysis Package v1 result for one Recording.
4. External database IDs are never trusted across machines.
5. Recording identity is resolved from stable semantic content, not local IDs or local filesystem paths.
6. No raw IQ content hash is required for M8.6B recording identity.
7. Canonical GroundTruth is mandatory in `recording_fingerprint_v1`.
8. All batch items are validated before the first ORM write.
9. All imported runs and detections are committed in one database transaction.
10. Re-importing the same semantic batch is idempotent.
11. M8.6B stops after import and returns an exact `Recording -> AnalysisRun` mapping.

## 4. Relationship to existing Analysis Package v1

Existing single-Recording Analysis Package v1 remains unchanged.

A child package keeps the current concepts:

- `manifest.json`;
- `detections.json`;
- optional `metrics.json` if declared by the child manifest;
- physical coordinates in seconds and absolute Hz;
- `class_id`, `class_name`, and `confidence` using the existing PackageDetection contract.

M8.6B does not introduce a second detection schema.

For M8.6B V1, the historical batch exporter writes child packages containing only:

- `manifest.json`;
- `detections.json`.

Child `results.metrics` is null/absent according to the existing optional field semantics. Child artifacts are not included in M8.6B V1.

The historical full-corpus metric report belongs in the outer batch metadata as a reference only and is never imported as an official DatasetEvaluation result.

## 5. Batch Analysis Package v1 layout

The archive layout is:

```text
<name>.analysis-batch.zip
|
|-- batch_manifest.json
`-- items/
    |-- 000000/
    |   |-- manifest.json
    |   `-- detections.json
    |-- 000001/
    |   |-- manifest.json
    |   `-- detections.json
    `-- ...
```

The outer manifest explicitly declares each child `package_path`. Import logic must not infer a child path from array position or item key.

The historical exporter uses deterministic zero-padded item keys and deterministic item ordering, but the schema does not require a particular child directory naming convention beyond safe, unique relative paths.

## 6. Batch manifest contract

### 6.1 Top-level fields

Batch Analysis Package v1 includes:

- `schema_version`: exactly `1`;
- `batch_id`: transport-facing identifier supplied/generated by the exporter;
- `pipeline`: common pipeline ID/name/version;
- `label_space`;
- `dataset`: common dataset name/split;
- `expected_items`;
- `execution`: outer execution description;
- `result_provenance`;
- `transport_provenance`;
- optional `recording_manifest_hash`;
- optional `historical_reference`;
- ordered `items`.

## 7. Recording identity across machines

### 7.1 Candidate selection

The importer first selects local Recording candidates by the tuple:

`dataset_name + dataset_split + Recording.name`

For the first historical import this is equivalent to:

`SpaceNet + test + sample stem`

A valid item must resolve to exactly one local candidate.

Outcomes:

- zero candidates: reject the batch;
- one candidate: continue to fingerprint validation;
- more than one candidate: reject the batch as ambiguous.

No latest/oldest/first-row fallback is allowed.

### 7.2 `recording_fingerprint_v1`

`recording_fingerprint_v1` is a SHA256 over canonical semantic content. It includes:

- dataset name;
- dataset split;
- label space;
- Recording name;
- data format;
- sample rate in Hz;
- center frequency in Hz;
- frequency low/high in Hz;
- number of complex samples;
- duration in seconds;
- canonical GroundTruth annotations.

Canonical GroundTruth is mandatory and contains:

- `t_start_s`;
- `t_end_s`;
- `f_low_hz`;
- `f_high_hz`;
- `class_id`;
- `class_name`.

GroundTruth ordering is deterministic by the same semantic key already used by M8.6A.

### 7.3 Canonical number formatting

M8.6B reuses the M8.6A canonical number formatting and ordering rules. Float values use the same stable `.17g` representation, with negative/positive zero normalized according to the existing M8.6A behavior.

The implementation may extract reusable canonicalization helpers from `backend/app/benchmarks/manifest.py`, but the existing M8.6A `recording_manifest_hash` must remain byte-for-byte stable for all existing inputs.

A regression test must prove that the refactor does not change the M8.6A manifest hash.

### 7.4 No raw IQ hash

`recording_fingerprint_v1` does not read and hash full IQ payloads.

SpaceNet identity may use file metadata such as file size indirectly to determine `num_samples`, as the existing SpaceNetAdapter already does, but it must not scan the approximately 30 GB test IQ corpus merely for identity verification.

### 7.5 Diagnostic fields

The item fingerprint carries both:

- the final fingerprint SHA256;
- human-readable stable metadata;
- `ground_truth_sha256`.

This allows mismatch errors to report useful field-level information rather than only `hash mismatch`.

## 8. Dataset recording manifest hash

`recording_manifest_hash` and `recording_fingerprint_v1` are different concepts:

- Recording fingerprint answers whether one local Recording is the same semantic sample.
- Dataset manifest hash answers whether the entire ordered dataset/GT snapshot is the same benchmark snapshot.

For generic Batch Analysis Package v1, outer `recording_manifest_hash` is optional.

For the first historical SpaceNet exporter, it is required and must be computed using the same M8.6A `build_recording_manifest()` semantics.

Before the first real local import, the batch outer hash must equal the local M8.6A prepare-manifest hash. A mismatch blocks import.

## 9. Outer/child consistency

After each child passes single-package validation, the importer verifies batch-wide invariants.

All child packages must agree with the outer manifest on:

- pipeline ID;
- pipeline version;
- label space;
- dataset identity represented by their recording context.

The importer also requires:

- unique item keys;
- unique package paths;
- unique Recording names within the batch;
- unique resolved local Recording IDs;
- `expected_items == len(items)`;
- total detections within safety bounds.

One local Recording cannot be referenced by two batch items.

Any mismatch rejects the entire batch.

### 9.1 Child Recording metadata rule

The outer manifest is authoritative for dataset name and split during batch matching.

For Batch Analysis Package v1 children produced by the M8.6B writer:

- child `recording.name` must equal the outer item `recording.name`;
- child `recording.dataset` is set to the outer `dataset.name`;
- dataset split remains an outer-batch field and is not encoded into the Analysis Package v1 child schema.

The importer must not parse free-form legacy dataset display strings to infer a split. This keeps the existing Analysis Package v1 schema unchanged while making M8.6B matching deterministic.

## 10. Batch archive safety

The existing M6 single-package extraction limits remain unchanged.

M8.6B adds a separate batch extraction entry point that reuses proven path and JSON safety primitives while using batch-scale limits.

V1 limits are:

- `MAX_BATCH_ITEMS = 10000`;
- `MAX_TOTAL_DETECTIONS = 1000000`;
- `MAX_BATCH_UPLOAD_BYTES = 256 MiB`;
- `MAX_BATCH_EXPANDED_BYTES = 1 GiB`;
- `MAX_BATCH_MEMBERS = 25000`;
- `MAX_JSON_BYTES = 32 MiB` per JSON document.

Batch extraction must retain protections for:

- Zip Slip/path traversal;
- Windows alias/ADS-style unsafe names;
- duplicate or case-colliding paths;
- encrypted members;
- links and special files;
- unreadable/corrupt ZIP data;
- missing required files.

M8.6B must not weaken M6 single-package limits merely to accommodate the batch format.

## 11. Reusable child validation

M8.6B must not loop over the current single-package `import_run()` function because that function commits one run at a time.

Instead, existing M6 validation semantics are factored into a reusable validation layer that can validate one extracted Analysis Package v1 without committing it.

The reusable validation path remains authoritative for:

- Analysis Package v1 manifest validation;
- required `detections.json` structure;
- PackageDetection schema validation;
- physical bbox validation against the selected Recording;
- label-space/class validation;
- confidence range validation;
- duplicate source detection ID validation;
- package execution metadata validation already required by M6.

The existing single-package import path must use the same validation core after the refactor and must preserve current M6 behavior.

## 12. All-or-nothing import transaction

Batch import has four phases.

### 12.1 Phase 1 - archive validation

- safely extract to a caller-owned temporary directory;
- parse/validate `batch_manifest.json`;
- validate paths and archive bounds.

No ORM write occurs.

### 12.2 Phase 2 - semantic validation

- bulk-load local Recording candidates for the selected dataset/split/label space;
- resolve every batch item;
- validate every `recording_fingerprint_v1`;
- validate optional/required dataset manifest hash according to the package context;
- validate every child Analysis Package v1;
- validate all detections;
- validate batch-wide common metadata and duplicate constraints;
- compute semantic import identity.

No ORM write occurs.

N+1 Recording lookups are not allowed.

### 12.3 Phase 3 - build ORM objects

Only after all validation succeeds, build in-memory:

- one `AnalysisRunModel` per batch item;
- zero or more `DetectionResultModel` rows per run.

Do not add these objects to the Session until validation is complete.

### 12.4 Phase 4 - one database transaction

Add all newly constructed runs and detections and commit once.

If any database/constraint failure occurs:

- rollback the transaction;
- leave zero new AnalysisRuns from this import;
- leave zero new DetectionResults from this import.

For the first historical batch this means approximately 2,500 AnalysisRuns and 33,373 DetectionResults in one successful transaction.

## 13. Imported AnalysisRun semantics

Each imported batch child becomes a normal:

- `executor = imported`;
- `status = completed`;
- `pipeline_id = outer/child pipeline ID`;
- `pipeline_version = outer/child pipeline version`.

Existing AnalysisRun schema is sufficient. No new database column is required.

`parameters_json` stores lightweight transport provenance, for example:

```json
{
  "package": {
    "pipeline_id": "...",
    "pipeline_name": "...",
    "pipeline_version": "...",
    "recording_name": "...",
    "dataset": "SpaceNet"
  },
  "batch_import": {
    "schema_version": 1,
    "batch_id": "...",
    "item_key": "000017",
    "package_path": "items/000017",
    "import_fingerprint": "...",
    "recording_fingerprint": "...",
    "archive_sha256": "..."
  },
  "source_detection_ids": {},
  "detection_count": 13
}
```

The exact JSON shape may be normalized during implementation, but the semantic fields above must remain available without introducing a BatchRun entity.

## 14. Semantic idempotency

### 14.1 Why ZIP SHA256 is insufficient

Archive SHA256 is a transport-integrity checksum only. It is not the semantic batch identity because compression level, ZIP timestamps, or member ordering may change archive bytes without changing predictions.

### 14.2 `batch_import_fingerprint_v1`

The importer computes a stable semantic fingerprint after validation.

It includes:

- batch schema version;
- common pipeline ID/name/version;
- label space;
- dataset name/split;
- stable result provenance;
- ordered item keys;
- each `recording_fingerprint_v1`;
- canonical child parameters relevant to the result;
- canonical final detections including source detection ID when present, physical bbox, class ID/name, confidence, and optional scores.

It excludes:

- `batch_id`;
- archive SHA256;
- ZIP compression details;
- ZIP member ordering;
- ZIP timestamps;
- `export_timestamp`;
- exporter/platform transport commit metadata;
- local DB IDs;
- local filesystem paths;
- generated AnalysisRun IDs;
- generated DetectionResult IDs.

Stable result provenance is included so two different frozen model/checkpoint results are not collapsed merely because their predictions happen to be identical.

### 14.3 Result versus transport provenance

`result_provenance` may affect `batch_import_fingerprint_v1`.

`transport_provenance` does not affect it.

For the first historical exporter, stable result provenance includes at least:

- frozen config SHA256;
- split manifest SHA256;
- source predictions SHA256;
- detector checkpoint SHA256;
- FRN checkpoint SHA256;
- source code commit if a trustworthy frozen commit is available.

Transport provenance may include:

- exporter version;
- platform repo commit used to package;
- export timestamp.

### 14.4 Duplicate import behavior

Before inserting new rows, the importer checks existing imported runs for the same semantic import fingerprint.

Outcomes:

- no matching items: normal new import;
- a complete matching set for all N item keys: return `already_imported = true`, create zero runs/detections, and return the existing exact mapping;
- a partial matching set: reject with `BATCH_IMPORT_STATE_INCONSISTENT`.

A partial prior state must never be silently repaired or supplemented.

## 15. Temporary archive lifecycle

M8.6B V1 does not permanently store the uploaded Batch ZIP or extracted child files in the platform data directory.

Flow:

```text
upload
  -> temporary safe extraction
  -> complete validation
  -> one database transaction or idempotent lookup
  -> response
  -> temporary files removed
```

The database preserves the standard DetectionResults plus transport/result provenance sufficient for normal platform use.

Raw Batch archives may be retained separately by the research/export workflow outside the application repository and runtime storage if the user wants archival copies.

## 16. Batch import API

The V1 endpoint is:

`POST /api/imported-runs/batch`

The operation is synchronous because it is bounded validation plus SQLite insertion, not model inference or benchmark computation.

M8.6B does not add a BatchImport job/status entity merely to background this operation.

A successful new import returns at least:

```json
{
  "batch_id": "...",
  "import_fingerprint": "...",
  "archive_sha256": "...",
  "dataset_name": "SpaceNet",
  "dataset_split": "test",
  "pipeline_id": "zoomspec_yolo26n_aug_combined_frn_v3",
  "pipeline_version": "1.0.0",
  "label_space": "spacenet_14",
  "item_count": 2500,
  "detection_count": 33373,
  "already_imported": false,
  "created_runs": 2500,
  "existing_runs": 0,
  "matched_recordings": 2500,
  "missing_recordings": 0,
  "ambiguous_recordings": 0,
  "fingerprint_mismatches": 0,
  "recording_run_mapping": [
    {
      "recording_id": "rec_...",
      "recording_name": "0",
      "analysis_run_id": "run_..."
    }
  ]
}
```

A successful idempotent re-import returns the same mapping with:

- `already_imported = true`;
- `created_runs = 0`;
- `existing_runs = N`;
- no new detections.

Validation failures use stable platform business errors and should identify the failing item key/Recording when possible.

## 17. Historical batch exporter architecture

### 17.1 Reuse the existing M9 bridge

The historical exporter reuses the existing M9.0 `LegacyDetectionAdapter` for legacy-to-platform detection conversion.

It does not reimplement historical bbox, class, or confidence semantics.

The existing frozen detection row maps:

- `sample_id` -> Recording name;
- `t0_s/t1_s` -> `t_start_s/t_end_s`;
- `f0_hz/f1_hz` -> `f_low_hz/f_high_hz`;
- `class_id` -> canonical `spacenet_14` class;
- final `score` -> platform `confidence`.

### 17.2 Generic writer plus historical adapter

M8.6B uses two layers:

```text
historical JSONL
  -> existing LegacyDetectionAdapter
  -> canonical platform detections grouped by Recording
  -> generic Batch Analysis Package writer
  -> .analysis-batch.zip
```

The generic writer knows Batch Analysis Package v1. The historical adapter knows the legacy JSONL. The writer must not know YOLO, AHLP, FRN, or RT-DETR internals.

### 17.3 No inference

The exporter must not:

- load detector or FRN checkpoints for inference;
- run STFT/LS-STFT;
- run AHLP;
- run GPU inference;
- recompute the final confidence score;
- change NMS or thresholds.

The frozen historical prediction JSONL is the prediction source of truth for this export.

## 18. Historical exporter inputs and provenance

The first real exporter consumes:

- frozen historical predictions JSONL;
- frozen SpaceNet test split manifest;
- SpaceNet advanced/test dataset directory;
- historical metrics report;
- frozen detector checkpoint path;
- frozen FRN checkpoint path;
- frozen full-pipeline config path;
- platform canonical label-space file;
- output path outside Git.

The exporter computes SHA256 values itself from the supplied frozen assets. Human copy/paste of hashes is not required for normal use.

## 19. Complete split coverage during export

The batch item universe is the frozen test split, not the set of sample IDs that happen to have predictions.

The exporter must create one child item for every test sample in the frozen split.

A Recording with zero predictions still gets:

```json
{
  "detections": []
}
```

This preserves 100% Recording coverage and distinguishes `no prediction` from `sample missing`.

The historical prediction JSONL must not contain sample IDs outside the frozen split. Unexpected sample IDs are an export error rather than being silently ignored.

All split sample IDs must resolve to actual SpaceNet sample metadata/GT.

## 20. Server-side recording fingerprints

The server exporter constructs recording identity from SpaceNetAdapter metadata and GroundTruth.

It may inspect `.bin` file size as part of existing SpaceNetAdapter sample metadata derivation, but it does not read full IQ payloads.

For every item, the exporter writes `recording_fingerprint_v1`.

For the first SpaceNet batch, the exporter also builds the complete M8.6A-compatible `recording_manifest_hash` for all 2,500 samples and writes it into the outer manifest.

## 21. Historical reference metrics

The historical metrics report is reference-only provenance.

For the first batch, the outer manifest may record:

- historical images: 2,500;
- historical canonical GT count: 19,962;
- historical predictions: 33,373;
- recorded mAP50: `0.49706861157413673`;
- recorded mAP50:95: `0.37325127587379914`;
- source report SHA256.

The importer must not copy these values into DatasetEvaluation tables.

M8.6C independently computes platform metrics from imported DetectionResults and local GroundTruth.

## 22. Deterministic export

The writer uses deterministic:

- dataset item order based on the M8.6A canonical Recording order;
- stable JSON serialization;
- deterministic ZIP member order.

The writer should fix ZIP timestamps where practical to improve byte-level reproducibility.

Archive SHA256 is still transport integrity only. Semantic idempotency remains based on `batch_import_fingerprint_v1`.

Repackaging the same semantic predictions with different transport timestamps or compression must not create a different semantic import fingerprint.

## 23. Historical exporter tests

Before the 2,500-sample export, run a tiny deterministic export test with at least:

- Recording A with two predictions;
- Recording B with zero predictions.

The test must prove:

- both Recording items are exported;
- the zero-prediction child is retained;
- child Analysis Package v1 manifests are valid;
- outer/child pipeline and label-space metadata agree;
- recording fingerprints include canonical GT;
- semantic batch fingerprint is stable across repackaging;
- archive ordering/serialization is deterministic to the extent promised by the implementation.

## 24. Batch importer tests

M8.6B importer tests must cover at least:

- Zip Slip/path traversal;
- duplicate/case-colliding ZIP paths;
- encrypted/link/special-file rejection;
- too many archive members;
- too many batch items;
- too many total detections;
- duplicate item key;
- duplicate package path;
- duplicate Recording name;
- two items resolving to one local Recording;
- missing child manifest;
- missing detections file;
- malformed child package;
- outer/child pipeline mismatch;
- outer/child version mismatch;
- label-space mismatch;
- zero local Recording candidate;
- ambiguous local Recording candidate;
- Recording metadata fingerprint mismatch;
- GroundTruth-only fingerprint mismatch;
- dataset manifest hash mismatch when present;
- duplicate detection source ID;
- invalid confidence;
- invalid physical bbox;
- invalid class label;
- zero-detection child succeeds;
- 2,499 valid + 1 invalid leaves zero new AnalysisRuns and zero new detections;
- successful import creates only standard AnalysisRuns/DetectionResults;
- first duplicate semantic import creates zero new rows and returns the existing mapping;
- partial prior semantic import state raises `BATCH_IMPORT_STATE_INCONSISTENT`;
- M6 single Analysis Package import remains behaviorally compatible after validation refactor;
- M8.6A recording manifest hash remains unchanged by any canonicalization refactor.

The server-side M8.6B acceptance run must use the frozen historical assets and report at least:

```text

label_space: spacenet_14
pipeline_id: zoomspec_yolo26n_aug_combined_frn_v3
pipeline_version: 1.0.0
```

The exporter records the actual `zero_detection_items` count rather than assuming it is zero.

No inference or training is executed as part of this acceptance.

## 26. Transfer integrity gate

After moving the generated archive from the server to the local Windows machine, recompute archive SHA256 locally.

The local archive SHA256 must equal the server-reported archive SHA256 before import is attempted.

This check validates transport integrity only.

## 27. First real local pre-import gate

The local platform must already contain the SpaceNet test dataset registered as:

- 2,500 Recordings;
- `dataset_name = SpaceNet`;
- `dataset_split = test`;
- `label_space = spacenet_14`.

Run the existing M8.6A prepare-manifest path and compute the local `recording_manifest_hash`.

The local hash must exactly equal the server-exported outer `recording_manifest_hash`.

If it differs, stop before batch import and investigate dataset/GT identity.

## 28. First real local import acceptance

A successful first import must report:

- `already_imported = false`;
- item count = 2,500;
- matched local Recordings = 2,500;
- missing Recordings = 0;
- ambiguous Recordings = 0;
- fingerprint mismatches = 0;
- created AnalysisRuns = 2,500;
- detection count = 33,373;
- returned Recording-to-AnalysisRun mapping length = 2,500.

Every imported run must be:

- executor `imported`;
- status `completed`;
